# GTSofia Live Map

Самостоятелна карта на живо за наземния градски транспорт в София. Проектът е отделен от основния сайт GTSofia и използва неговите GTFS данни за маршрути, спирки и геометрии.

## Какво включва

- Интерактивна карта с Leaflet и OpenStreetMap.
- Позиции на автобуси, трамваи и тролеи, получавани през WebSocket.
- Превключване между източниците GTFS и AVL.
- Филтри по вид транспорт, линия и инвентарен номер.
- Изчертаване на маршрута на избрана линия и показване на спирки при достатъчно приближение.
- Списък с превозни средства, скорости, направление, последно обновяване и закъснение, когато източникът подава необходимите данни.
- Светла/тъмна тема и бутон за геолокация.
- Адаптивен интерфейс, вдъхновен от визуалния език на GTSofia: Sofia Sans, светлосив фон, бели панели, заоблени карти и минималистични контроли.

## Стартиране локално

Страницата зарежда JSON файл през `fetch`, затова я стартирай през локален HTTP сървър, а не чрез отваряне на `index.html` директно от файловата система.

С Python:

```bash
python -m http.server 8080
```

Отвори `http://localhost:8080`.

Или използвай Live Server във VS Code.

## Публикуване като отделно GitHub репо

1. Създай празно GitHub repository, например `gtsofia-livemap`.
2. Качи всички файлове от тази папка в root директорията на новото repository.
3. В GitHub отвори **Settings → Pages**.
4. Под **Build and deployment** избери **Deploy from a branch**, branch `main`, folder `/ (root)`, и запази.
5. След публикуване картата ще бъде достъпна на адреса на GitHub Pages за новото repository.

Няма нужда от npm build — това е статичен сайт с vanilla JavaScript и CDN версия на Leaflet.

## Live data: важно

В `src/config.js` са зададени двата WebSocket адреса, използвани от референтната реализация на Dimitar5555:

- GTFS: `wss://sofiatraffic-proxy.onrender.com/v2/livemap/`
- AVL: `wss://sofiatraffic-proxy.onrender.com/livemap/`

Това позволява да се използва същият тип поток на живо, но означава, че позициите зависят от наличността и съвместимостта на този външен proxy. Картата не генерира фалшиви маркери, ако потокът не работи. За независима продукционна версия е препоръчително да разположиш собствен backend/proxy за потока от ЦГМ и да промениш адресите в `src/config.js`.

Кодът приема JSON съобщения с масив от превозни средства; всяко превозно средство трябва да включва поне координати `coords: [latitude, longitude]` и идентификатор. Поддържат се полетата `cgm_id`, `inv_number`, `route_ref`, `type`, `speed`, `timestamp`, `destination_stop`, `scheduled_time` и `occupancy`, когато са налични.

## Данни за маршрути и спирки

`data/transport-map.json` е олекотен набор, генериран от `data/transport.json` в основния проект GTSofia. Включва линии за наземен транспорт, спирки, последователности на спирките, геометрии на маршрутите и съществуващите line overrides. Таблиците с разписания и пътувания са изключени.

За да е по-бързо зареждането, геометриите са опростени с допуск 8 метра, а JSON съдържа само необходимите полета. Размерът на набора е приблизително 1,4 MB вместо десетки мегабайти за целия файл с транспортните данни.

За обновяване на набора след ново генериране на `data/transport.json`:

```bash
python scripts/make-map-data.py /path/to/gtsofia/data/transport.json
```

По подразбиране скриптът обновява `data/transport-map.json` в текущата папка. Можеш да подадеш друг път с `--output` или да настройваш степента на опростяване с `--tolerance-m` (стойност в метри; по-малко число пази повече детайл).

## Корекции във версия 2

- Информацията за превозното средство се слива между последователните live съобщения: липсващи полета не заличават вече получен модел, инвентарен номер, следваща спирка, скорост или разписание.
- Видът транспорт се нормализира по полето от потока, маршрута и наличните line overrides; добавена е и корекция за известните заместващи автобуси.
- Списъкът с линии се ограничава до GTFS маршрути с налични направления и геометрия в компактния набор, за да не показва неизползвани route записи.
- Добавени са иконите `bus.svg`, `tram.svg`, `trolley.svg`, `night-bus.svg` и останалите SVG от папката `Icons/Active icons` на основния GTSofia проект.
- Popup-ът вече използва идентичност на линия тип иконка + цветен pill, показва инвентарния номер без „МПС“, модела, а за следващата спирка — име и код, когато кодът се разпознава.
- `src/models.js` съдържа справочни модели, адаптирани от `Dimitar5555/sofiatraffic-livemap/data/models.js`. Логиката за „необичайно“ от `expected_models.js` умишлено не е добавяна на този етап.

Източник на транспортните иконки: основният GTSofia проект (папка `Icons/Active icons`).

### Проверки на версия 2

Компактният GTFS пакет към 09.10.2026 съдържа 137 маршрута с налична геометрия за наземен транспорт (121 различни номера/имена на линии). Dropdown-ът вече се изгражда само от тези маршрути; при номера, използвани от повече от един вид транспорт, етикетът показва всички типове.

Логиката за „необичайно“ не е активирана, защото тя изисква отделния каталог `expected_models.js` и допълнителни справочни данни за депата/очакваните модели по линии. Това остава изолирано за следваща версия.


## Версия 3 — live разпознаване и минимален интерфейс

- Справочникът за разпознаване включва всички GTFS маршрутни записи, включително тези без геометрия. Само списъкът във филтъра се ограничава до маршрутите, за които има валидни shapes.
- Полетата за тип, маршрут, инвентарен номер и timestamp се извличат и от алтернативни имена в live payload-а. Когато типът липсва, се използват CGM ID/override-ите и еднозначните инвентарни диапазони от каталога с модели.
- Превозни средства със сигнал, по-стар от 1 час, не се показват. Възрастта се оценява по timestamp в източника, а не само по момента на получаване от proxy-то.
- Live визуализацията се събира в един `requestAnimationFrame`, не създава маркери извън видимата област и сменя иконката само когато се променят важни за нея полета. Отвореният popup не се прерисува по-често от веднъж на 8 секунди.
- При клик върху превозно средство се чертае ненатрапчива, полупрозрачна полилиния за маршрута му. Popup-ът е по-компактен и показва инвентарния номер на мястото на премахнатото „Обновено в“.
- Интерфейсът е опростен: navbar `GTSOFIA /livemap`, sidebar само с филтри, карта без допълнителните инфо-панели и с икона за местоположение под zoom бутоните.
- Нощните линии използват `#000000` за цвета на pill-а.

### Проверки във версия 3

- JavaScript синтаксисът е проверен с Node.js.
- Проверени са локално примерни live записи за `TB37`, `TM37`, `A183`, запис без маршрут, инвентарен номер в еднозначен трамваен диапазон и сигнал отпреди 5 часа.
- Проверено е, че кодът за неактуални записи отстранява сигнали над 1 час и че цветовете за нощни линии са черни.
- Не беше възможна надеждна браузърна визуализация в тази среда; затова окончателното поведение на външните WebSocket потоци остава за проверка след публикуване.


## Версия 4 — направление и popup

- При избор на превозно средство се чертае само една посока от линията; изборът използва налични direction ID/headsign/destination данни и fallback спрямо близостта и ориентацията на превозното средство към геометрията.
- Полилинията е с непрозрачност 100% (`opacity: 1`).
- В popup-а дестинацията се показва до иконата `destinationarrow.svg`.
- Марката/моделът е поставен под „Следваща спирка“; текстовите полета за вида транспорт и номера на колата са премахнати. Остават инвентарният номер, скоростта, закъснението и последният сигнал.


## Версия 5 — атрибут за модел, непълни live полета и плавно движение

- Марката/моделът е отделен атрибут със заглавие „Марка/модел“ и стойност отдолу, оформен като останалите полета в popup-а.
- Когато live потокът изрично подаде празен номер на линия, дестинация или следваща спирка, интерфейсът премахва старата стойност. Ако поле изобщо липсва в частично съобщение, се пази последната известна стойност, за да няма мигаща/изчезваща информация.
- Превозни средства без разпознат номер на линия остават на картата, показват „—“ вместо номера и използват цвета по подразбиране според вида транспорт. При неразпознат и вид транспорт се използва неутрален цвят.
- Имената на спирките се резолвират от включения GTFS справочник; кодът/следващата спирка и дестинацията се обновяват от последните live съобщения, като отвореният popup може да се обнови до около 1,2 секунди след новите данни.
- Между последователни координати маркерът се движи плавно с `requestAnimationFrame` и smoothstep интерполация. Кратки нормални премествания се анимират за приблизително 0,5–1,4 секунди; големи скокове се задават директно, за да не се рисува фалшиво движение през града при GPS корекция.
- Съобразено с референтния проект на Dimitar5555: моделът и следващата спирка са отделни от данните за линията, а имената на спирките се намират чрез справочника им. В тази версия няма добавена нова зависимост или backend.

### Ограничение на актуалността на статичните имена

Live стойностите за следваща спирка/дестинация се обновяват при пристигане на нови съобщения. Самите имена и координати на спирките идват от `data/transport-map.json` (GTFS snapshot в repository-то) и ще се променят само след обновяване и публикуване на този файл.


## GTFS live processing parity (2026-10-10)

The live map intentionally uses **GTFS only**. Its WebSocket endpoint is the same v2 endpoint used by [Dimitar5555/sofiatraffic-livemap](https://github.com/Dimitar5555/sofiatraffic-livemap): `wss://sofiatraffic-proxy.onrender.com/v2/livemap/`. AVL is not configured or used.

GTFS processing now follows the reference workflow more closely:

- Route number and vehicle type are resolved from `cgm_route_id` via the same [route metadata catalog](https://github.com/Dimitar5555/sofiatraffic-schedules/blob/master/data/routes.json), with a synchronized local fallback in `data/route-catalog.json`.
- Partial snapshots are merged into a stable cached vehicle object, preventing markers and popup callbacks from retaining outdated data.
- The same special bus corrections are applied for temporary `TM/TБ` route labels and the known fake-trolley routes.
- Vehicle heading is derived from consecutive positions while moving, and inactive entries are hidden but retained in the cache so a later fresh GTFS record can reactivate them.
- The selected vehicle's route geometry is recalculated when GTFS updates change the resolved direction or shape.
- WebSocket errors and closes use a single guarded reconnect timer. The socket is not started if the static route/stop dataset failed to load.
- Static datasets use revalidation and versioned script URLs to reduce stale browser-cache mismatches.

The WebSocket server is an external service. This repository controls the client-side GTFS processing, but cannot guarantee the upstream service's availability or force it to include fields that it does not send.
